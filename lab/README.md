# Shahrah censorship lab

A reproducible, root-only lab built from Linux network namespaces (tested on WSL2 Ubuntu 24.04).
It runs the real pinned data planes (Xray REALITY/XHTTP, Hysteria2, WaterWall, paqet) and the
real Shahrah brain/oracle against a scripted censor, then writes `RESULTS.md` and `results.json`.

```
client ── censor ── iran ── inet ──┬── exit   (Xray, Hysteria2, WaterWall exit, paqet server)
10.0.1.2   (DPI,    10.0.2.2       ├── cover  198.18.5.2 (HTTPS/HTTP origin + REALITY target)
           tc,dns)  (WaterWall     
                     iran relay)
```

The cover sits in the RFC 2544 benchmark range (198.18.5.2, routed only inside the lab) on
purpose: Shahrah's Hysteria2 ACL and Xray's routing refuse egress to private ranges, and Xray 26's
freedom outbound additionally blackholes reserved ranges (TEST-NET etc.), so a cover on 10.x or
198.51.100.x is (correctly) unreachable through the tunnels.

## Run

```
sudo lab/run.sh            # topology, data planes, matrix + brain scenario, teardown
sudo lab/run.sh brain      # failover scenario only
KEEP=1 sudo lab/run.sh     # leave everything up; then lab/censor.sh <profile> by hand
sudo lab/planes.sh down; sudo lab/topo.sh down
SHAHRAH_LAB=1 sudo pytest -m lab   # same thing as a pytest (excluded by default)
```

Binaries are fetched into `/root/shahrah-lab-bin` and verified against the sha256 pins in
`deploy/install.sh`. All keys/certs are generated per run under `/run/shahrah-lab` and removed
on teardown; nothing secret is written into the repo.

## Censor profiles (`lab/censor.sh`)

| profile | what the censor does (only on traffic leaving the client) |
|---|---|
| open | nothing |
| sni-dpi | nfqueue DPI (`dpi.py`, stdlib): RST on non-allowlisted SNI and on SNI/IP mismatch (allowlisted name sent to an IP it does not resolve to) |
| udp-block | drop all UDP except DNS |
| udp-throttle | hashlimit UDP above 60 pps (burst 30) |
| allowlist-ip | only the iran relay and the cover IP are reachable |
| icmp-only | only ICMP passes |
| dns-poison | resolver answers a sinkhole for non-allowlisted names |
| lossy-mobile | netem ~150 ms RTT, ±30 ms jitter, ~4 % round-trip loss |
| shutdown | everything dropped |

## What this lab can and cannot prove

It can show: which path survives which *mechanism*; that configs generated by Shahrah actually
interoperate with the pinned binaries; that the oracle changes mode and the brain fails over
when the network changes under it; rough relative latency under loss.

It cannot show:
- **Real Iranian DPI.** The censor is a few iptables rules and an SNI parser. No ML/flow
  classification, no active probing of the exit, no TLS-fingerprint (JA3/JA4) blocking, no
  per-ASN or time-of-day policy. "Works here" is necessary, not sufficient.
- **Real-world timing.** Everything runs on one host; absolute numbers are loopback-scale.
  Only `lossy-mobile` adds realistic delay, and netem loss is uniform, not bursty like 4G.
- **Iran↔exit censorship.** The censor sits only on the client leg; the iran→exit leg is clean.
- **CDN / domain-fronting paths.** Not modelled (open).
- **Throughput and fairness at scale**, many users, or carrier NAT behaviour.
- WSL quirks: DNS lookups from WSL to the outside are slow (~8 s), so the lab pins every name
  in per-namespace hosts files and its own resolver; WSL2 NAT is not involved in-lab.

Known, expected result: `relay-ww` (client → iran relay with SNI `cover.lab`) trips the
SNI/IP-mismatch rule under `sni-dpi`, because the iran IP is not where `cover.lab` resolves.
A real deployment needs an SNI that resolves to (or is plausible for) the relay's IP.
